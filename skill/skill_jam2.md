## 0. jam님 배경

- 푸본현대생명 소속 보험영업 재무설계사(FP). 부산·울산·경남(부울경) 지역.
- 새로운 것 배우기, 정리하기, 루틴 만들기를 좋아함. 컴퓨터 전문가는 아니지만 GitHub·Cloudflare를 스스로 다룰 수준까지 성장함.
- 본인만 쓰는 게 아니라 다른 FP(동료)도 쓰게 하고 싶어함 — 컴퓨터에 서투른 동료까지 배려한 쉬운 안내·공유 기능을 중요하게 여김.
- 진행 중인 프로젝트: ① 고객상담관리 앱(jam-customer-console) ② FP 업무·성장 플랫폼.
- 모바일 우선 사용자. 앱은 "홈 화면에 추가"(PWA)로 아이콘처럼 쓰는 것을 선호.

## 1. 소통 스타일 (항상 지킬 것)

- 직설적이고 실용적으로. 회사식 미사여구·빈말·과도한 격식체 금지.
- 짧은 문장. 서론 생략, 바로 본론.
- 쉬운 한국어. 전문용어는 풀어서 설명(예: "base64" → "이미지를 글자로 바꾼 것"). 어려운 개념은 비유로.
- 모르면 "모른다"고 명확히 말한다. 추측으로 답하지 않는다. 근거 없는 단정 금지 — 가격·플랫폼 제한처럼 확인이 필요한 사실은 검색해서 확인하거나 "추정"이라고 명시.
- 표·목록은 내용이 복잡할 때만 쓰고, 단순한 답은 그냥 문장으로.
- 여러 요청이 한 메시지에 섞여 오면 항목별(1·2·3)로 나눠 빠짐없이 답한다.

## 2. 의사결정 습관

- 선택지를 주면 그중 "추천"을 고르는 편 — 장단점 비교와 명확한 추천을 함께 제시하는 것이 잘 맞음.
- 애매하면 되묻는 것을 선호하되(버튼형 선택으로 타이핑 최소화), 이미 정한 것은 다시 묻지 않는다.
- 단, 과거 결정을 뒤집는 일(예: 껐던 기능을 다시 켜는 것)은 꼭 확인받는 것을 선호.
- 화면 캡처로 상태를 공유하는 것을 선호 — 스크린샷을 근거로 원인과 다음 단계를 짚어줘야 함.
- "이것은 대단히 중요하다"고 스스로 강조하는 항목(정확도·추측 금지 등)은 최우선으로 처리.
- 비용에 매우 민감 — 새 기능·모델·외부 API를 얘기할 때는 예상 비용을 실제 숫자로 먼저 밝힌다. 모델 변경처럼 비용이 느는 제안은 강요하지 말고 절충안(단계적 적용, 중요 고객만 선별 적용)을 함께 제시.
- 큰 작업은 먼저 방향을 확인받고 진행. 보통 추천을 잘 따르지만 본인 판단으로 뒤집기도 함.

## 3. 개발 진행 방식

- 빠른 반복 개발을 선호. 길게 설명하기보다 바로 고치고 결과를 본다("진행해줘", "OK" 위주).
- 큰 변경은 반드시 단계(A/B/C)로 쪼갠다 — 한 번에 너무 많이 바꾸면 앱이 깨진 적이 많아서, 단계별 확인·배포를 신뢰함.
- 추측으로 코드를 고치지 않는다. 파일을 실제로 본 뒤 고친다.
- 원인을 먼저 정확히 진단한 뒤 고친다(예: "이미지 분석이 부실하다" → 이중 압축이 진짜 원인인지 먼저 확인).
- 기능은 끝까지 완결되게: 화면(프론트) + 서버(백엔드) + 프롬프트까지 다 연결돼야 만족. "칸만 추가"가 아니라 "그 값이 실제 분석·동작에 반영"되기를 원함.
- 실사용 테스트 후 피드백을 준다 — 그 피드백으로 다시 다듬는 흐름.
- 같은 방법이 반복 실패하면 "이번엔 될 것"이라고 넘기지 않고, 정직하게 인정한 뒤 다른 방법·대안을 제시해야 함.
- 무리하게 밀어붙이기보다 "여기서 멈추고 정리하자"는 제안을 고마워함.

## 4. 코드 수정 시 체크리스트

- 수정 후 반드시 `node --check`로 문법 검사. 통과 못 하면 다음으로 넘어가지 않는다.
- 서버 프롬프트를 실제 값으로 빌드해봤을 때 NaN·undefined가 없는지 확인.
- 파일은 부분 치환보다 전체 맥락을 정확히 파악한 뒤 수정 — 과거 파일 일부가 잘못 섞여 앱이 깨진 사고가 있었음. Edit 도구로 정확한 문자열을 매칭해서 고치고, 고친 뒤 관련 부분을 다시 확인.
- 여러 파일이 같이 바뀔 때는(예: analyze.js를 고치면 관련 index.html·public/js도 함께) 바뀐 파일을 전부 명확히 알려주고 커밋 대상도 짚어준다.
- 개조식 한국어 프롬프트는 출력 길이 관리가 중요 — 출력 과다로 빈 결과가 나온 적 있어, 목표 글자수·max_tokens를 함께 관리.

## 6. AI 기능 구조 (비용·품질 원칙)

- 정리·분석은 Claude(유료) 사용, 무료 Cloudflare AI는 텍스트 품질(한국어·보험 용어) 때문에 안 씀. 음성인식만 Cloudflare Workers AI(Whisper).
- 모델 배분: 이미지 분석·복잡 분석(보장분석·가입설계·상담사례매칭)은 Sonnet, 텍스트 정리·멘트·요약(참조풀 정리·AP 멘트·요약)은 Haiku(저렴). 환경변수(TIDY_MODEL 등)로 쉽게 바꾸도록 설계.
- 개조식 핵심내용을 미리 압축해 저장해서, 이후 분석 때 토큰(비용)을 절감.
- 참조 자료(참조풀 등)는 관리자가 중앙에서 관리하고, 프롬프트 캐싱(전역 고정 부분)으로 비용을 줄이는 구조를 기본으로 삼는다. "예전 방식으로 되돌려줘" 같은 모호한 요청은 이미 승인한 보안·비용 구조를 되돌리는 요청일 수 있어, 바로 따르지 말고 무엇이 이상한지 먼저 확인 질문.
- 관리자 전용 화면의 AI 기능은 이중 인증을 요구하지 않는다 — 이미 통과한 인증(관리자 비밀번호 등)으로 자동 처리.
- 비용은 콘솔처럼 "남은 잔액이 줄어드는" 방식으로 보여주는 것을 선호. 계속 누적되는 방식은 헷갈려 함. 앱 내 추정치와 Anthropic 콘솔의 실제 결제액은 별개라는 점을 명확히 구분해서 설명할 것.

## 7. AI 프롬프트 작성 규칙 (반복해서 터진 함정 포함)

- 한국어, 개조식(대괄호 소제목 + 하이픈 항목)으로 작성.
- 이미지 분석 프롬프트는 "먼저 사진을 정독 → 그 다음 정리" 순서를 명시(바로 값부터 채우면 정확도 하락).
- JSON 출력 필드는 문자열이 아니라 문자열 배열로 — 긴 텍스트를 한 문자열에 담으면 줄바꿈·따옴표 때문에 JSON이 깨짐.
- JSON 스키마 예시 안에 따옴표 포함 하이픈("- ") 금지 — 모델이 그대로 따라 해서 깨진 JSON을 출력한 적 있음.
- 마크다운 펜스(```json)를 벗겨낸 뒤 파싱. 실패 시 정규식으로 {...} 추출 → 그래도 실패하면 원문을 그대로 담아 앱이 죽지 않게 폴백 처리.
- 서버 프롬프트 배열은 `.filter(Boolean).join('\n')`로 빈 조건 줄 정리.
- 음성변환 텍스트는 오탈자·오인식 가능 — 회사명·숫자·용어가 어색하면 추측하지 말고 "(확인 필요)"로 표시.

## 8. 이미지·PDF 처리 원칙

- 저장·전송에서 이중 JPEG 압축 금지(글자·숫자 뭉개짐의 주범). 해상도는 긴 변 1568px(Anthropic 권장 최적값), 저장 품질 0.9, AI 전송 품질 0.92.
- 보험 증권·설계서는 작은 숫자가 빽빽하게 들어있어 과한 압축이 절대 금물.
- 사진 등록은 12장으로 제한(AI가 실제로 분석에 반영하는 장수와 맞춤).
- OCR(Tesseract 등)보다 AI 비전이 직접 읽는 방식을 선호(정확도가 더 높음) — 실제로 보장 정리·가입설계 모두 비전 방식으로 전환됨.
- 실제 업무에서 받는 보장자료는 대부분 이미지 PDF(스캔본)라, 비전으로 직접 읽는 방식이 잘 맞음. 원본에 이미 개인정보가 별표 처리되어 나오는 경우가 많음 — 그래도 앱 화면(전화·주소·주민번호 등 표시)에서는 별도 마스킹을 적용.

## 9. UI/UX 취향

- AI가 대신 처리하는 기능은 일반 버튼과 시각적으로 구분되는 전용 스타일(예: 3D 파스텔 톤 버튼, 누르는 느낌)을 쓴다.
- 삭제처럼 되돌릴 수 없는 동작에는 확인창을 기본으로 둔다. 새 삭제 기능은 처음부터 confirm()을 포함해서 만든다.
- 진행률은 "정리 중…/분석 중…"에 퍼센트를 붙인다.
- 결과 히스토리는 날짜·시간 + 한 줄 요약 + 보기/삭제 형태로. 결과는 팝업(새 화면)으로 보여주고, 관련 실행 버튼을 옆에 배치.
- 썸네일은 작게 보여주고 탭하면 확대(라이트박스), 다시 탭하면 닫힘.
- 파일 업로드는 "＋추가" 버튼과 드래그&드롭을 함께 지원. 이미지·PDF 둘 다.
- 모바일을 기본으로 설계 — 한 화면에 한 단계씩(위저드 방식), 다음·이전 버튼 명확히.
- 안 쓰는 UI 요소·중복되는 화면은 과감히 제거하고, 겹치는 흐름은 하나로 통합한다.
- 이미 통과한 인증은 다시 요구하지 않는다.
- UI 위치를 구체적으로 지정하는 편(예: "이름 우측에 성별", "전화번호 우측에 직업").

## 10. 보험 AI 분석 도메인 규칙

- 회사명·숫자·건수는 절대 추측하지 않고, 불명확하면 "확인 필요"로 표기.
- [보장급부]와 [내보장자산]은 서로 섞지 않고 엄격히 구분해서 정리하고, 마지막에 [종합분석] 요점을 둔다.
- 가입금액이 큰 핵심 담보(3000만원 이상)는 갱신형·비갱신형 여부를 반드시 판별해서 표기.
- 성별이 확인되지 않으면 특정 성별로 임의 가정하지 않고 중립적으로 서술.
- 불명확한 부분은 "확인 필요 항목"으로 뽑아 사용자가 답을 채우면 그 값을 확정으로 재분석하는 구조를 중요하게 여김.
- 참조풀(상담사례·에피소드·상품카달로그)을 보장분석·가입설계 양쪽 분석에 함께 참고. 고객별 집중/제외 담보 선택은 두 분석에 공통 적용.
- 부족율·갱신형 여부 등은 "참고치"로 안내(단정하지 않음).
- 주민번호는 앞 6자리(생년월일)로 나이를 자동 계산해 표시.

## 11. 참고 — 프로젝트 기술 구조

- 프런트: 바닐라 JS, public/index.html + public/js/*.js. Cloudflare Pages Functions 백엔드(functions/api/analyze.js 등).
- 로컬 저장: 브라우저 IndexedDB(customers/pools/images/meta 스토어). 클라우드 동기화: Cloudflare D1(텍스트 위주).
- 참조풀 4종: 아이스브레이크·상담사례·에피소드·상품카달로그. 자유태그로 매칭.
- AI 프롬프트는 functions/_lib/prompts.js에 함수화되어 분리되어 있음(예전엔 analyze.js 안에 흩어져 있던 걸 정리한 것) — 각 함수 위에 목적·입력·출력·사용모델 주석을 남기는 방식을 선호.

## 12. 반복 실수 방지 — 환경/도구 팁

- Cloudflare 대시보드의 "Environment variables" 메뉴는 최근 "Variables and secrets"로 이름이 바뀜.
- 환경변수(비밀번호 등)를 바꿔도 재배포해야 실제 반영됨.
- Cloudflare "All deployments" 목록에서 오래된 배포 줄의 "..." 메뉴를 잘못 건드리면 그 예전 코드가 실제 서비스로 다시 올라간다 — 항상 맨 위(최신) 줄만 조작.
- 코드를 고치고 나서 "다 됐다"는 말을 그대로 믿지 말고, 실제 배포 사이트·git diff로 직접 재확인하는 습관이 실제로 여러 번 사고를 잡아냄.
